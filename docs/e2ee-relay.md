# 端到端加密中继

推荐部署把信任放在自己的电脑与手机上，Hub 只是一个可替换的密文信箱：

```text
个人 Agent ──本地加密──→ 官方 / 自建 / 公益 Hub ──密文──→ Android
个人 Agent ←─本地解密─── 官方 / 自建 / 公益 Hub ←─密文── Android
```

## 一次性配对

运行 `captchamesh start` 后，打开终端显示的本机链接；电脑在本地生成 256 位配对密钥。
Hub 创建邮箱和 60 秒有效、只能
领取一次的 join token；二维码同时携带 Hub 地址、邮箱 ID、join token 和配对密钥。配对
密钥不会发送给 Hub。Android 领取自己的设备 token 后，把 token 和配对密钥用 Android
Keystore 加密保存；电脑状态文件权限固定为 `0600`。

二维码应当当作临时密码处理：只在自己的屏幕显示，不截图分享。若怀疑泄露，重新配对；
旧邮箱不能据此推导新邮箱密钥。

## 消息与 Hub 能看见什么

任务和结果使用 HKDF-SHA-256 派生的方向密钥以及 AES-256-GCM 加密。邮箱 ID、消息 ID、
方向、过期时间和密文长度是路由所必需的元数据，会被 Hub 看见。以下内容只在端点解密：

- CAPTCHA 类型、网址、site key 和页面上下文
- Cookie、User-Agent、localStorage 与代理信息
- 图片、坐标、旋转值、Token 和类型化答案

每条消息的邮箱、ID、方向和过期时间都放入 GCM 附加认证数据；篡改会导致端点拒绝。
Node 和手机使用不同方向密钥，Hub 还会强制设备角色与方向匹配、拒绝重复消息 ID，并在
确认或过期后删除密文。

## 后台行为

手机配对并允许通知后，会运行 `remoteMessaging` 前台服务，通过出站 HTTPS 长轮询等待。
通知只显示“个人 Agent 需要你验证”，不会在系统通知或服务日志中展示网址和任务内容。
用户点开通知后，App 才在本机解密并展示挑战；不会自动代答或后台抢任务。

这是默认 Agent API 模式的链路：电脑 Agent 提交任务后自动通知手机，不要求用户先在 App
启动工作流。手机主动启动固定脚本时走可选的工作流节点协议，脚本遇到 CAPTCHA 后仍复用同一
人工验证界面。

## Hub 类型

- 官方 Hub：开箱即用，仍按不可信中继设计。
- 自建 Hub：部署 `deploy/hub/`，域名必须使用有效 HTTPS。
- 公益 Hub：协议与官方相同；客户端通过 `/.well-known/captchamesh` 检查协议版本和限制。

公益 Hub 无需发行贡献币。更适合公开带宽、在线率、保留时间和滥用限制，并允许运营者自愿
署名。可交易积分会引入刷量、套利、结算和监管问题，与个人低频人工接管的定位不匹配。

Hub 永远不托管端点密钥，也不能向电脑下发命令。电脑上能启动什么仍只由本机
`registrations.json` 白名单决定。

本地 2Captcha 兼容桥的安装和 Agent 接入见 [`local-bridge.md`](./local-bridge.md)。
